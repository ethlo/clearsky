Jira

This runs acli jira auth login --web, which opens the Atlassian login in your browser. Clearsky stores no Jira credentials.

Google Calendar

Option A, no new login: add your work Google account in your desktop's Settings → Online Accounts → Google, with Calendar switched on. Enter your work email below and save. Clearsky reads the calendar GNOME syncs.

Add a personal Google account in Online Accounts (Calendar only) to see family appointments here too. On a shared calendar (one not named after your address, like "Family"), events only take your time when you're invited, or when one of these names is in the title; the rest just show in the agenda.

Option B, iCal link (only if your admin allows it). You can use both; meetings are merged:

  1. Open Google Calendar settings.
  2. Under Settings for my calendars, click your calendar, then Integrate calendar.
  3. Copy Secret address in iCal format and paste it below.

Slack

  1. Create the Clearsky Slack app (pre-filled; pick your work workspace).
  2. Click Install to Workspace. Your admins may need to approve it.
  3. Under OAuth & Permissions, copy the User OAuth Token (xoxp-…) and paste it below.

General

Team pack

Your team's shared setup (organizations, stand-up time, links, Copilot skills), from a git repo, an https link or a file the team keeps. Settings you changed yourself are kept. clearsky team export makes one from your settings.

Set-up check

What this machine has for Clearsky (gh, acli, Copilot, the sandbox, a calendar) and how to get what's missing: the welcome page, or clearsky doctor in a terminal.

Demo

Clearsky with made-up data, in a new tab: for showing it to others without your own work on screen. Nothing of yours is read or shown, and it stops when you click Leave demo in its menu.

Copilot

Defaults for a new chat. The pickers in a chat still change that chat.

Where a chat runs when it isn't about a PR or ticket. Chats about a PR or ticket run in that repo's clone, or the worktree with the PR's branch. Clearsky's own skills (stand-up, triage) are available only from the Clearsky folder.

Comma-separated, like ~/dev/work, ~/dev/mine. Copilot can read and change files there, including worktrees next to your clones, without the "Access paths outside trusted directories" question. Commands and edits still follow the access mode. Empty means ~/dev. Running chats pick changes up on their next message.

Comma-separated. In the sandbox, Copilot can read these but not change them. It can also always read (what it needs to run and build) and files outside your home, like /usr/lib/jvm. The rest of your home is hidden from it: mail, documents, browser profiles, shell history and logins. Maven still reaches your repositories: Copilot gets a copy of ~/.m2/settings.xml without the passwords, and the sandbox adds your login on the way out, only to the hosts that login is for.

In the sandbox, Copilot runs everything without asking, and asks you only at its doors out: git push and GitHub changes (held at the sandbox's network until you click Allow), Jira changes through acli, and outside (a command run on your machine, like tests that start Docker containers). Jira and outside commands that start like one of these (comma-separated) go through without asking. outside commands only match exactly, like outside ./mvnw verify.

With the sandbox on, Copilot and everything it runs can write only in the chat's folder, the folders above, ~/.copilot and /tmp, can read only the parts of your home listed under Also readable (never ~/.ssh, keyrings, browser profiles or Clearsky's own settings), and can reach only the hosts below. That holds in every access mode, Full included. The Sandboxed access mode always runs in it, and then runs every step inside without asking; only its doors out ask (see Never ask before). srt comes with Clearsky (Linux also needs bubblewrap, socat and ripgrep). Hosts are checked by name only: an allowed host can be written to as well as read. Your GitHub login never enters it: Copilot, git and gh inside get stand-ins, and the sandbox's proxy adds your gh login on the way to GitHub. Reading GitHub goes through; a push or any change (a PR, a comment, a review) waits until you click Allow in the chat. Inside it, git reaches GitHub over https instead of ssh.

Not needed: by default the sandbox uses your gh login. If you can create a fine-grained token (with Copilot Requests), the sandbox uses it instead, for example one that can only read your work repos. Either way it stays out of the sandbox and changes still wait for your Allow.

When a sandboxed chat is done, it ends the PR description (and the ticket description, if it wrote that) with a line like Implemented with Copilot (Claude Opus 5.5). 939 credits used. The model and credits come from the chat's own session log, through Clearsky. Applies to chats started after you switch it on.

Comma-separated, wildcards like *.atlassian.net allowed. Empty means Copilot, GitHub and your Jira site. Add package registries (say repo.maven.apache.org, registry.npmjs.org) if builds need them.

Comma-separated, for private images tests need (say from your company's registry): a whole image like registry.example.com/team/app:main, or a name prefix like registry.example.com/ (then the newest tag of each image there). Before each vm command, the ones your own Docker has are copied into the chat's VM if it doesn't have that version yet. Your registry login never goes in the VM. The VM gets what your Docker has: docker pull on your machine when the image changes.

Kinds of change you said to always allow, from the Allow, and always for… button on a card. Each still shows in the chat and in Copilot's changes. merge-ready: merging a PR of the chat's repo when CI is green, it's approved and has no conflicts. delete-merged-branch: deleting a branch whose PR is merged. repo:owner/name: everyday changes to that repo from any chat. jira:KEY: changes to tickets in that Jira project. Remove one to be asked again.

For each chat's VM. Empty uses the default shown: half this machine's cores (up to 12) and a quarter of its memory (4 to 16 GB). Memory the VM doesn't use stays yours. Kept within this machine: at most all its cores and half its memory. Applies to the next VM a chat starts; the first one after a change takes about 15 seconds longer (it saves a new snapshot).

How many chats can have a VM running at once (1 to 8, empty is 1). Another chat's vm command waits in line and its chat shows where it is. A VM with nothing running in it gives its place to the next in line; it starts again, from the snapshot, on its chat's next command.

Memory

Notes every new chat reads, kept in ~/.local/share/clearsky/memory/memory.md on this machine. Copilot is told never to change this file (in the sandbox it can't): it suggests notes in the chat, and they're saved only when you press Save on the card. Put notes for one repo under a ## owner/name heading.

Grafana

Lets Copilot read logs and metrics of your environments with grafana logs test '{app="api"} |= "error"' instead of a shell on servers. Read only: Clearsky makes only search and query calls, with your Viewer login, which never goes in the sandbox. Secrets it knows the shape of are removed from what comes back, every call is in Copilot's changes, and the environments below that ask do so in the chat every time.

One per environment, as name=address. Kept in your settings file only.

Not needed: log in below with your browser instead. If you can create a Grafana service account with the Viewer role, its token (name=glsa_…) is used instead of the login.

A host (or URL) behind your work VPN. Off the VPN it either can't be reached or refuses you with 403, as many work sites do at their load balancer; then the menu says VPN off, Grafana and the modules listed next pause instead of failing, and Copilot is told to ask you to connect. Clearsky never runs the VPN itself.

Modules

What each part of Clearsky holds and talks to; click one for the details. Saved secrets are never shown, only whether one is there. Each source gets only its own settings, and a source that lists its hosts can reach only those through Clearsky.
